# Nocturnal — reference for agents

Generated by the Nocturnal engine. Do not edit by hand; it is rewritten on Rescan and when the engine updates. The short version lives in this project's `AGENTS.md`.

## `.nocturnal/project.json`

Operational config plus an `intelligence` section (a BuiltWith-style stack scan written by the adoption agent — regenerated by Rescan, not something to hand-edit).

**Keep the operational fields true.** If you change a port, a dev command, or a script in the repo (vite/next config, `package.json`, a new service), update the matching field here in the same change. The engine watches this folder and the dashboard follows on its own.

| Field | What it is / when to touch it |
| --- | --- |
| `id` | Stable slug, lowercase and hyphens. Never rename it — process ids and port claims key off it. |
| `name` | Human-readable project name. |
| `displayName` | Rail override the user set from the dashboard. If present, leave it alone. |
| `description` | One line on what this project is. |
| `github` | `{ owner, repo }`, from the git remote. Drives the Issues, CI, and PR tabs. |
| `services` | Declared ports: `{ name, port, url?, purpose?, preview? }`. Update when a dev port moves. |
| `processes` | Long-running commands: `{ id, name, command, cwd, autostart?, restartOnCrash? }`. Dev servers, watchers, compilers. |
| `processGroups` | Things that start together: `{ id, name, processIds }`. Processes only, never scripts. |
| `scripts` | One-shot commands: `{ id, name, command, cwd, kind }` where kind is deploy · build · test · util · custom. These become buttons. |
| `links` | Project URLs: `{ name, url }`. Production, staging, docs, admin panels, design files. |
| `favicon` | Repo-relative image used as the rail mark. There is no in-app icon picker. |
| `versionSections` | Changelog headings for this project, e.g. `["Features", "Fixes", "Infrastructure"]`. |
| `firebaseProjectId` | Firebase project id, when the repo deploys to one. |
| `focusIdentifier` | Bundle id / app identifier used to focus the running app. |

```json
{
  "id": "my-app",
  "name": "My App",
  "github": { "owner": "you", "repo": "my-app" },
  "services": [{ "name": "web", "port": 5173, "url": "http://localhost:5173" }],
  "processes": [
    { "id": "web", "name": "Web dev", "command": "npm run dev", "cwd": ".", "autostart": false, "restartOnCrash": true }
  ],
  "processGroups": [{ "id": "dev", "name": "Everything", "processIds": ["web", "api"] }],
  "scripts": [
    { "id": "deploy", "name": "Deploy", "command": "bash scripts/deploy.sh", "cwd": ".", "kind": "deploy" }
  ],
  "links": [{ "name": "Production", "url": "https://example.com" }],
  "versionSections": ["Features", "Fixes", "Infrastructure"],
  "favicon": "static/icon.png"
}
```

Alongside it: `versions.json` (release log — `currentVersion` plus `entries`) and `plans.json` (roadmap — plan text, status, issue link, timestamps; any agent can read and run a ready plan).

## `.nocturnal/runtime.json` — optional, what is running right now

`project.json` says what this project *has*; `runtime.json` says what is *up*, and is how the dashboard opens a browser preview the moment a dev server is reachable. Write it from the process that actually binds the port — it is the only thing that knows the URL it got.

```json
{
  "version": 1,
  "services": [
    { "name": "web", "url": "http://localhost:5173", "port": 5173, "kind": "web", "ready": true, "preview": true }
  ],
  "updatedAt": "2026-09-18T09:00:00.000Z"
}
```

| Field | Meaning |
| --- | --- |
| `version` | Contract version. Currently `1`. |
| `services[].name` | Short label, matched against `project.json` services by port where both exist. |
| `services[].url` | Where to reach it **on this machine**. |
| `services[].port` | The listening port. Without it the engine cannot confirm the service is up. |
| `services[].kind` | `web` (default), `api`, or `worker`. Only `web` is previewed. |
| `services[].ready` | Your claim that it is serving. |
| `services[].preview` | Show this one first when several are up. |

Three rules the engine enforces, so write the file honestly rather than optimistically:

- **The engine reads this file. It never executes anything in `.nocturnal/`.** If you need to compute the state, do it in your own process — register it in `processes` and let the engine run it as a normal dev process.
- **`ready` is a claim, not proof.** The engine cross-checks every entry against its own port scan. A service claiming `ready: true` on a port nobody is listening to is shown as unconfirmed and never opens a preview.
- **Nothing here grants anything.** It cannot change permissions, and it cannot assert that a deploy succeeded.

Write it atomically (temp file then rename) — the engine watches the folder and a half-written file is simply ignored until the next write.

## Driving the engine

Everything the engine does is one envelope — `{ "type": "proc.logs", "payload": { "id": "my-app-web" } }` — reachable three ways. Use whichever is already wired up:

- **MCP** — the `nocturnal-mcp` server exposes every command as a tool, named by swapping the dot (`proc.logs` → `proc_logs`). Each tool carries its own parameter schema, so list the tools rather than guessing at payloads.
- **CLI** — `noc cmd proc.logs id=my-app-web lines=80`, or `--json '{…}'`. `noc commands [query]` prints all 169 with their params; `-g Processes` narrows to one group, `--json` makes it parseable.
- **HTTP** — `POST http://127.0.0.1:17410/cmd`, browsable at `/api-docs`.

| Tool | For |
| --- | --- |
| `proc_list` · `proc_logs` | Is my dev server up, and why did it die |
| `proc_restart` · `proc_startGroup` | Bounce a process after a config change |
| `script_run` | Run a script declared in project.json (deploy, seed, migrate) |
| `issue_create` · `issue_update` · `issue_comment` | File and close work on the GitHub repo |
| `plan_create` · `plan_build` | Park a roadmap item, or hand a ready plan to an agent |
| `ports_kill` · `port_fixConflicts` | Free a port, or remap this project off a clash |
| `git_refresh` · `github_createPR` | Re-read git status; open a pull request |

Read-only commands are safe to call unprompted. The rest change real state — don't stop processes, launch agents, or file issues you were not asked to.

## Processes and logs

Nocturnal owns long-running commands for this project. Do **not** start `npm run dev` in a leftover terminal if Nocturnal should own the process, and do **not** kill ports by PID. If something is down or crashing, **read the process log first**.

**Statuses:** `starting` · `online` · `stopping` · `stopped` · `crashed` · `errored`. A def in `project.json` with no registry row is idle until first start. Stopped rows stay in the list; they disappear only on delete. The registry id is `{projectId}-{process.id}`.

**Logs** live on the machine running the engine:

- Process: `~/.nocturnal/logs/proc-<id>.log` (rolls to `.1` at ~5MB)
- Script run: `~/.nocturnal/logs/script-<projectId>-<scriptId>-<runId>.log`
- Quickest read: `noc logs <id> -n 80`, or the `proc_logs` tool.

The dashboard Processes tab shows CPU/RSS and an inline log tail; **Open in Terminal** runs `tail -f` on the same file. Script history (20-run ring plus lifetime ok/fail counters) is on the `scriptRuns` topic.

PM2 is not the runtime and must not be assumed.

## Ports

Declared in `services[]`. Live sockets and conflicts are on the `liveStatus` / `portConflicts` topics and the dashboard Ports card. Overlapping declared ports show a dashboard note (cannot run both projects at once). `port.fixConflicts` remaps conflicting ports on **this** project; `port.rotate` moves every declared service onto registry-allocated free numbers. Syncing project info writes the real ports and does not remap.
