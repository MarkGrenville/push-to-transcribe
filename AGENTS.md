## Nomad IDE Integration

This project is managed by [Nomad](https://github.com/MarkGrenville/nomad-ci), a multi-project mission control for agent-era development. A per-device daemon (port 4100) monitors this project's ports, processes, git status, CI, issues, and versions in real time and surfaces them in a dashboard (port 4101) and IDE sidebar.

### How Nomad uses this project

- **`.nomad/project.json`** — Project configuration and deep intelligence scan. Contains operational config (services, processes, scripts, links) plus a rich `intelligence` section with BuiltWith-style analysis of the tech stack, third-party services, architecture, and conventions. This file is generated by an AI scan and can be regenerated via the "Rescan" button in the dashboard.
- **`.nomad/issues/`** — Lightweight issue queue (markdown files with YAML frontmatter). Agents can create issues here and they appear in the dashboard.
- **`.nomad/versions.json`** — Version log tracking releases with changelogs.

### What agents can do to help Nomad

- **Add scripts**: If you add useful one-shot commands (deploy, seed DB, run migrations, generate types, etc.), add them to the `scripts` array in `.nomad/project.json` so they appear as runnable buttons in the dashboard.
- **Add processes**: Long-running dev commands (watchers, dev servers, compilers) go in the `processes` array (`id`, `name`, `command`, `cwd`). Nomad starts them detached — they survive a daemon restart. The registry id is `{projectId}-{process.id}`.
- **Add links**: Project-relevant URLs (staging, production, docs, admin panels, design files) can be added to the `links` array.
- **Create issues**: Drop a markdown file in `.nomad/issues/` with the frontmatter format: `id`, `title`, `status` (open/in_progress/review/done/shipped), `priority` (low/normal/high/critical), `created`, `updated`.

### Process manager — how to track and read logs

Nomad owns long-running commands for this project. Do **not** use PM2, do **not** start `npm run dev` in a leftover terminal if Nomad should own the process, and do **not** kill ports by PID. If something is down or crashing, **read the process log first**.

**Statuses:** `starting` · `online` · `stopping` · `stopped` · `crashed` · `errored`. A def in `project.json` with no registry row is idle until first start. Stopped rows stay in the list; they disappear only on delete.

**Where logs live (on the machine running the Nomad daemon):**
- Process: `~/.nomad/logs/proc-<id>.log` (rolls to `.1` at ~5MB)
- Script run: `~/.nomad/logs/script-<projectId>-<scriptId>-<runId>.log`

**How to list / start / stop / read (same verbs, three routes):**

1. CLI: `nomad proc ls` · `nomad proc logs -k <id> -n 80` · `nomad proc start -p <projectId> -c "<command>" --cwd <path>` · `stop` / `restart` / `delete` · `save` / `resurrect`
2. MCP tools: `proc_list`, `proc_logs`, `proc_start`, `proc_stop`, `proc_restart`, `proc_delete`
3. HTTP: `POST http://127.0.0.1:4100/cmd` with `{ "type": "proc.logs", "payload": { "id": "<id>", "lines": 80 } }`

The dashboard Processes tab shows CPU/RSS and an inline log tail; **Open in Terminal** runs `tail -f` on the same file. Script history (20 stored, 5 shown) is on the `scriptRuns` topic — open a history ball for that run's log.

**Ports:** declared in `services[]`. Live sockets and conflicts are on the `liveStatus` / `portConflicts` topics and the dashboard Ports card. Overlapping declared ports show a dashboard note (cannot run both projects at once). `port.fixConflicts` remaps **this** project's ports onto registry-allocated free numbers. Adopt writes the real ports and does not remap.
