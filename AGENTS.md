## Nocturnal Integration

This project is managed by [Nocturnal](https://github.com/MarkGrenville/nomad-ci), a multi-project mission control for agent-era development. A per-device engine monitors this project's ports, processes, git status, CI, issues, and versions, and surfaces them in a dashboard and IDE sidebar.

The long version lives in `.nocturnal/guide.md`, which the engine rewrites on Rescan — read that rather than editing it.

### Files in `.nocturnal/`

- **`project.json`** — Operational config (services, processes, scripts, links, `favicon`, `focusIdentifier`) plus an `intelligence` section: a BuiltWith-style stack scan written by the adoption agent. Regenerated by Rescan, so don't hand-edit `intelligence`.
- **`versions.json`** — Release log (`currentVersion` plus `entries`).
- **`releases.json`** — Components, releases and promotion policy.
- **`issues/`** — Lightweight issue queue: markdown files with `id`, `title`, `status` (open/in_progress/review/done/shipped), `priority` (low/normal/high/critical), `created`, `updated` frontmatter.
- **`runtime.json`** *(optional)* — What is actually up right now, written by whichever process binds the port. Not used here: this is a menu bar app with no services.

### Keeping the operational fields true

If you change a port, a dev command, or a script in the repo, update the matching field in `project.json` in the same change. The engine watches the folder and the dashboard follows on its own.

- **Add scripts**: one-shot commands (build, export, clean) go in `scripts` as `{ id, name, command, cwd, kind }` where kind is deploy · build · test · util · custom. These become dashboard buttons.
- **Add processes**: long-running commands go in `processes` as `{ id, name, command, cwd }`. The registry id is `{projectId}-{process.id}`.
- **Add links**: project-relevant URLs go in `links`.

### Driving the engine

Every command is one envelope — `{ "type": "proc.logs", "payload": { "id": "push-to-transcribe-app-console" } }` — reachable three ways:

1. **MCP** — the `nocturnal-mcp` server exposes each command as a tool, named by swapping the dot (`proc.logs` → `proc_logs`). List the tools rather than guessing at payloads.
2. **CLI** — `noc cmd proc.logs id=<id> lines=80`, or `--json '{…}'`. `noc commands [query]` lists them all; `-g Processes` narrows to one group.
3. **HTTP** — `POST http://127.0.0.1:17410/cmd`, browsable at `/api-docs`.

Read-only commands are safe to call unprompted. The rest change real state — don't stop processes, launch agents, or file issues you were not asked to.

### Processes and logs

Nocturnal owns long-running commands for this project. Do **not** leave the app running from a stray terminal if Nocturnal should own the process, and do **not** kill ports by PID. If something is down or crashing, **read the process log first**. PM2 is not the runtime and must not be assumed.

**Statuses:** `starting` · `online` · `stopping` · `stopped` · `crashed` · `errored`. A def in `project.json` with no registry row is idle until first start. Stopped rows stay in the list; they disappear only on delete.

**Logs** live on the machine running the engine:

- Process: `~/.nocturnal/logs/proc-<id>.log` (rolls to `.1` at ~5MB)
- Script run: `~/.nocturnal/logs/script-<projectId>-<scriptId>-<runId>.log`
- Quickest read: `noc logs <id> -n 80`, or the `proc_logs` tool.

### Ports

This project declares no services — it is a menu bar app, not a server — so the Ports card stays empty. If that ever changes, declare them in `services[]` so the engine can track conflicts.

## This app's own diagnostics

Separate from Nocturnal, the app writes its own log, which is usually the faster way to debug a recording or transcription problem:

- `~/Library/Logs/PushToTranscribe/push-to-transcribe.log` (rolls to `.1` at 5MB)
- Archived audio and transcripts: `~/Library/Application Support/PushToTranscribe/voice-archive/`
